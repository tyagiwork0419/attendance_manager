# 0004. v1ではキャッシュ層を追加しない

## ステータス
承認済み

## コンテキスト

GAS版では、[0001](0001-execution-layer-migration.md)の背景にある速度改善策
として、`CacheService`を使い年ファイルのID解決・年一覧・祝日カレンダーの
取得結果をキャッシュしていた（打刻のたびに毎回Driveフォルダ検索が走ることが
最大のボトルネックだったため）。Vercel Functionsへの移行にあたり、同種の
キャッシュを持つかどうかを決める必要がある。

## 検討した選択肢

- **選択肢A: Upstash Redis等の外部キャッシュストアを使い、GAS版と同じ
  キャッシュ戦略を再現する**
  確実に速いが、[0003](0003-session-token-strategy.md)で見送ったのと同じ理由
  （追加の外部サービス契約、0001の「追加インフラは持たない」という方針との
  不整合）で、v1のスコープとしては過剰と判断した。
- **選択肢B（採用）: v1ではキャッシュを持たず、Sheets/Drive/Calendar APIを
  素直に呼ぶ**
  今回の移行そのものの目的（GASの実行環境オーバーヘッドを取り除くこと）
  だけで、キャッシュ無しでも十分な改善が見込める。GASが遅かったのは
  「実行環境の起動・スプレッドシートを開き直すコスト」であり、
  Sheets/Drive/Calendar APIを直接呼ぶだけでもそのオーバーヘッドは無くなる。

## 決定

v1では追加のキャッシュ層を持たない。年ファイルの解決、年一覧、祝日カレンダー
の取得は、リクエストのたびにGoogle Sheets/Drive/Calendar APIを呼ぶ。

## 結果・トレードオフ

**得られるもの**: 追加インフラなしで実装がシンプルに保てる。キャッシュの
無効化・整合性を考える必要がない。

**引き換えに受け入れるコスト**: GAS版のキャッシュほどの速さは出ない
可能性がある。

**見直す条件**: 本番移行後に実測した体感速度・レイテンシがまだ不十分な場合は、
Upstash Redis等を使ったキャッシュ層の追加を再検討する（このADRを廃止し、
後継ADRを作る）。
