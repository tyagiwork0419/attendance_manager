# 0003. 本人確認セッションはステートレスな署名付きトークンにする

## ステータス
承認済み

## コンテキスト

共有端末や他人の分のタイムカードを開くときの「本人確認セッション」
（`login`で発行、既定6時間で失効）は、GAS版では`CacheService`（サーバー側の
一時ストア）にセッション情報を保存し、トークンはそのキーとして使っていた。

Vercel Functionsはリクエストごとに独立したサーバーレス関数で、インスタンス間
で共有されるメモリを前提にできない。GASの`CacheService`に相当する状態保存を
続けるには、何らかの外部ストアが必要になる。

## 検討した選択肢

- **選択肢A: Upstash Redis等をセッションストアとして使う**
  GASの`CacheService`に最も近い構成。ただし0001で決めた「実行層だけ差し替え、
  追加インフラは持たない」という方針に反し、新たに外部サービスの契約
  （Vercel Marketplace経由のUpstash等）が必要になる。Vercel KVは2024年末に
  廃止されておりMarketplace経由の契約が前提になる。
- **選択肢B（採用）: サーバー側で状態を持たない署名付きトークン
  （HMAC-SHA256で `{name, exp}` を署名）にする**
  検証は署名とexpiredチェックだけで完結し、外部ストアが不要。

選択肢Bが安全に成立する理由: GAS版のセッションにも取り消し（revoke）の仕組みは
元々無く、TTL経過で失効するだけだった。署名付きトークンも同じ振る舞い
（有効期限が来るまで有効、途中で無効化はできない）なので、移行による
セキュリティ上の後退はない。取り消しが必要な端末トークン（`devices`シートの
`revoked`列）は今回の対象外で、これまで通りシートで管理する。

## 決定

ログイン成功時に、`{name, exp}` をHMAC-SHA256で署名した文字列
（`base64url(payload).base64url(signature)`）をセッショントークンとして発行する
（`server/src/crypto.ts`の`signSessionToken`/`verifySessionToken`）。署名鍵は
Vercelの環境変数（`SESSION_SECRET`）で管理する。有効期限は管理者設定の
`sessionTtlSeconds`をそのまま使う。

## 結果・トレードオフ

**得られるもの**: 追加の外部ストア無しでセッション機能を移行できる。検証が
純粋関数になりテストしやすい。

**引き換えに受け入れるコスト**: 発行済みトークンを個別に無効化する手段がない
（GAS版から変わらない制約）。`SESSION_SECRET`が漏れると、有効期限内であれば
任意の名前のセッションを偽造できてしまうため、他のサービスアカウント鍵と
同様に環境変数として厳重に扱う必要がある。
