# 0001. 実行層をGoogle Apps ScriptからVercel Functionsへ移行する

## ステータス
承認済み

## コンテキスト

勤怠管理アプリのバックエンドはGoogle Apps Script (GAS) のWebアプリだった。
GASは1リクエストごとにスプレッドシートを開き直し、`DriveApp`のフォルダ内検索
（年ファイルの解決など）を伴う処理が特に遅く、既にサーバー側キャッシュ
（`CacheService`）で緩和したものの、実行環境そのもののオーバーヘッドは
取り除けず、体感速度への不満が残っていた。

一方で、勤怠データは今まで通りGoogleスプレッドシート上に置いたまま維持したい
という要望がある。管理者が打刻データや設定を直接スプレッドシートで確認・編集
できる今の運用（八木さんが`users`シートを直接編集する等）を変えたくないため。

## 検討した選択肢

- **選択肢A: GASのまま、キャッシュ等でチューニングを続ける**
  実装コストは最小。ただしGASの実行環境自体のオーバーヘッド（スプレッドシートを
  開き直すコスト、Drive APIの遅さ）は原理的に消せず、改善に上限がある。
- **選択肢B: データもFirebase/Supabase等の専用DBへ全面移行する**
  最も速く、最もスケールする。ただし「スプレッドシートを直接編集する」という
  今の運用ができなくなり、管理用の画面を別途作る必要が生じる。
- **選択肢C（採用）: データはスプレッドシートのまま、実行層だけ差し替える**
  Google Sheets/Drive/Calendar APIをサービスアカウント経由で叩く、
  Vercel Functions (Node.js) のバックエンドに置き換える。
  GASの実行オーバーヘッドを取り除きつつ、スプレッドシートを直接編集する
  運用は維持できる。

Vercel FunctionsとCloudflare Workersを比較した。Cloudflare Workersはエッジ実行
で理論上より速く無料枠も大きいが、V8 isolateランタイムのためNode.js APIが無く、
Google Sheets APIのサービスアカウント認証（JWT署名）を自前実装する必要があり、
実装リスクが上がる。Vercel Functionsは公式の`googleapis`/`google-auth-library`
（Node.js）がそのまま使え、GitHub連携での自動デプロイもFlutter WebのGitHub
Pagesデプロイと同じ運用に揃えられる。本番の勤怠データを扱う以上、実装の
手堅さを優先しVercelを選んだ。

## 決定

データはGoogleスプレッドシートに置いたまま、実行層をGAS Web App から
Vercel Functions (Node.js、TypeScript) に置き換える。クライアント（Flutter Web）
との通信仕様（1エンドポイントへのPOST、`action`ベースのディスパッチ、
`{ok:true,result}` / `{ok:false,error,code}` のレスポンス形式）は完全互換を
保ち、クライアント側の変更は`Constants.webAppUrl`の向き先変更のみに留める。

移行は段階移行ではなく一括切り替え（ユーザーの意向）。新バックエンドを
`server/`ディレクトリに作り切り、Puppeteer等で本番スプレッドシートに対して
一通り動作確認したうえで`Constants.webAppUrl`を切り替える。GASのデプロイは
切り戻し用にすぐには消さない。

## 結果・トレードオフ

**得られるもの**: GASの実行オーバーヘッドが無くなり、体感速度が改善する見込み。
TypeScript + Vitestによるテスト・型チェックの規律も入る。

**引き換えに受け入れるコスト**:
- 新たにGoogle Cloudのサービスアカウント作成・スプレッドシート/フォルダ/
  カレンダーの共有設定という、GASには無かった初期セットアップが必要になる
  （`server/README.md`に手順書を用意する）。
- バックエンドのホスティング先がGoogleアカウント内で完結しなくなり、
  Vercelという別プラットフォームへの依存が増える。
- 見直す条件: 将来、打刻の記入方法自体を変える（スプレッドシート直接編集を
  やめる）ことになれば、選択肢Bを再検討する余地がある。
